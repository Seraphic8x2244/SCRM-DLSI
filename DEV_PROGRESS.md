### Design audit — evidence and five-chat contract (historical baseline; Chats 1–2 now completed)

**Product goal:** build complete, target-relevant *possible explanations* for an ambiguous spell immune event from real Spell.dbc metadata; do not conflate a candidate with an observed immune dimension. No creature-ID/spell-ID exclusions. Retain the event-source boundary and distinguish Nampower raw `IMMUNE` and `IMMUNE2`. The interpretation of either raw event is not invented from server-source assumptions; per-effect immunities may be *possible*, never conclusively attributed without matching evidence.

**Verified DLSI source seams** (current single `SCRM-DLSI.lua`; approximate lines as of 0.1.19-dev):
1. `Pipeline.GetSpellProfile` (~595–691) already reads school, spell-level mechanic, three `effectMechanic` entries, effect metadata (`auraName`, effect ID), `dispelType` and optional `targetCreatureType`. It exposes per-effect `mechanicDimension`, `profile.mechanicDimensions`, and cache. **Issue:** aura fallback can classify an unrecognised nonzero effect mechanic as if it were unset; aggregate fallback inclusion depends on a spell-wide `explicitMechanicDimension` flag, which can hide valid per-effect fallback dimensions. Preserve effect index and classification source.
2. `hypothesisCandidates` (~2458–2507) currently returns a flat dimension list for `failurePath=="whole_spell"`: school, spell-level mechanic and dispel dimension; it **does not explicitly collect all effect-level possibilities** on that path. `effect_mask_zero` returns no candidates. Importantly, a spell-level Root mechanic can already enter the current list, so the prior conversational claim that Root is *always* excluded from Frost Nova is **incorrect**. At least one earlier stored Frost Nova hypothesis contained Frost+Root. Candidate completeness depends on exact DBC spell-level/effect fields.
3. `createHypothesis` (~3218 onward) eliminates candidates using previously saved `vulnerable` facts and immediately calls `confirmSingleCandidate` if one remains. Known immune/dynamic/transient and unresolved-identity protections already exist; keep them.
4. `planAfterAuthoritativeSuccess` (~2845 onward) later reduces persisted hypotheses and **also promotes a one-survivor hypothesis**; this is a second confirmation path requiring the same proof guard.
5. `successDimensions` (~2409) records landed school damage or successful applied debuff/aura dimensions; it currently returns empty if the static spell profile is nil, even when valid runtime-school damage is available. Audit this loss without broadening attribution to unsupported effects. The existing success effect-index ambiguity and dispel-vulnerability interpretation need targeted regression checks.
6. HearthDB schema **v2** stores `facts(mob_id,dimension,verdict,dynamic_suspected,proof_source,proof_spell_id,proof_event)`, `hypotheses`, and `hypothesis_candidates`; this preserves the last proof rather than full combat history. v1→v2 repair and `dlsi_aura_repair_backup` must remain compatible.

**Concrete motivating evidence:** a prior uploaded v1 HearthDB contained `root=vulnerable` from Growl (AuraType 11, Taunt, wrong legacy mapping) on Mr. Smite and Captain Greenskin and `frost=immune` with `proof_source='ambiguous_whole_spell'`, spell 122 (Frost Nova), `SPELL_MISS_OTHER:immune`. Magic-dispel vulnerability had also been learned. Eliminating previously recorded Root and Magic alternatives could make Frost the sole candidate under existing confirmation rules. This is a **credible causal reconstruction, not a full replayed event history**; the DB lacks the timeline. In that uploaded snapshot there were **four** stored permanent `ambiguous_whole_spell` immune facts: two Frost from Frost Nova and two Fear from Psychic Scream (8122), requiring general review; actual users' current DBs can differ. The aura-v2 migration removes demonstrably misclassified Growl evidence but does not automatically retract derivative Frost confirmations.

**Proposed exact implementation:**
- **Profile model:** for each active/target-applicable effect slot (up to three) track `effectIndex`, effect ID, mechanic ID, aura type, explicit vs fallback source, inferred dimension and applicability/unknown classification. Use authoritative spell-level mechanic separately; use aura fallback **only when that effect's mechanic is zero**, not when it is unknown-but-nonzero. Handle `MOD_ROOT` 26 correctly. If targeting data is unavailable or a nonzero field cannot be classified, preserve an incomplete/unknown alternative rather than inventing certainty. Audit available actual ClassicAPI/C_Spell/DBC fields before depending on new API access.
- **Candidate model:** return a structured description (dimension + origin + evidence class/effect index) covering school, spell-level mechanic, every supported target-applicable effect mechanic/aura fallback, and dispel family. Deduplicate dimensions without losing provenance. Include an `unmodelledAlternative` or equivalent completeness flag. E.g. Frost Nova can have potential Frost/Root/dispel_magic alternatives, but **not proof** that Root caused the event; no fabricated cause from vMaNGOS's `IMMUNE` nomenclature.
- **Raw miss semantics:** preserve `IMMUNE` vs `IMMUNE2` normalization at the observation seam; only generate a causal suspicion from a failure path where doing so is justified by raw event and validated metadata. `IMMUNE2` should not suddenly generate durable permanent mechanism facts merely because Spell.dbc lists a root effect. Unsupported/unknown targeting and effect types block definitive deduction, not entire reporting/diagnostics.
- **Confidence/promotion rule:** candidate elimination by legitimate `vulnerable` evidence may narrow a hypothesis but **must not by itself manufacture an `immune` fact** from an ambiguous event. Both immediate and later confirmation routes need one shared `CanConfirmFromEvidence`-style gate. Permit confirmed immune only on attributable authoritative failure or a fully justified/exhaustively validated inference scenario; exact criteria for such an exceptional case must be specified and tested before enabling it. Identical generic IMMUNE repeats are not independent attribution. A one-candidate ambiguous result should remain `suspected` unless the proof gate passes.
- **Success/revocation:** keep genuine school damage and positively observed effect/aura applications as vulnerability evidence; preserve DR, temporary immunity, reflection, death, target identity, dynamic-suspected safety and provider three-state truth. Fix valid runtime-school damage loss if profile absent, but do not use uncorrelated or wrong-target damage. Check that `[immune]`/ `[noimmune]` unresolved results remain unknown, and that broad six-school spell immunity is not silently promoted by speculative facts.
- **Storage/history:** after behavior tests, design **schema v3** migration from v2. Re-evaluate *all* historical facts promoted from `ambiguous_whole_spell` under the new confidence rule using stored proof source/spell metadata, not creature names/IDs or spell-ID allow/deny lists. Archive unsupported conclusions, retract to unknown, and keep separately established successful evidence. Conservative handling of old hypotheses whose candidate lists omit alternatives or whose original causal context cannot be reconstructed: preserve as uncertain or back up and retire; **never silently manufacture confirmed evidence**. Ensure v1→v2→v3 sequential upgrade, atomic versioned operations, no startup full reset, idempotence, fail-closed metadata/SQL errors, rollback safety, and restore/recovery documentation. The four example immune facts require inspection under the general policy, not automatic unconditional deletion by spell ID.
- **Scope:** core DLSI `dev` only for this redesign. Host `immunities-hook` requires no learner changes unless integration proves an API defect. Never modify `main`, `dev_rulebook.md`, stable releases or unrelated repos without separate approval.

## Product / architecture contract
- Companion plugin to SCRM (Vanilla WoW 1.12.1 / Lua 5.0.3). DLSI owns advanced immunity observations, transient safety, learning, persistent HearthDB knowledge, diagnostics, alerts and UI; SCRM stays an independent macro host.
- Exactly **one** DLSI Lua file; preserved original internal module sections and listener/inference logic: Observations, Storage, Transient, Knowledge, UI. The original source was consolidated into five private loader functions; learner algorithms, success/ambiguous IMMUNE paths, target safeguards, uncertainty, DR/TempCC/reflection/death exclusions and hypothesis persistence must remain unchanged. Do not transplant unrelated fork Utility/Core code.
- Distinct Lua 5.0 `setfenv` loader environments and DLSI facade; no `_G.CleveRoids` module rebinding or host-global method overrides. Read-only private spell/effect/dispel, GUID/live creature-ID, aura/DR helpers adapt to the *frozen generic host*, not to fork-only prototype extensions.
- **One** normalized event source: the pre-existing private Observations frame; no duplicate normalized listener/router. It calls the original learner path only if initialization succeeded **and** the live selected provider is `scrm-dlsi`. Switching to Built-in stops DLSI learning immediately; host built-in automatic learning is dormant for the entire duration an external provider is selected, including missing/error/unknown. Host owns account-wide selection, no DLSI shadow selection or fallback.
- Provider registers through `CleveRoids.RegisterImmunityProvider("scrm-dlsi", "SCRM Deep Learning Immunities", check)` **only after** storage init and original module loading. The callback returns `true` for confirmed immunity/live applicable guard, `false` only for sufficiently evidenced vulnerability on complete applicable dimensions, `nil` for missing evidence, insufficient identity, unsupported/incomplete spell profile, unresolved classification, storage failure or other uncertainty. A broad `all`, `spell` or `cc` immunity can override positively; absence of broad negative facts does not block a proved exact vulnerability. No host legacy automatic learner data supplies DLSI answers. For player targets only proven live aura can return true; never consult NPC-template facts.
- Bare and named `[immune]`/`[noimmune]` use frozen host's existing macro front door and return semantics. In particular, a selected external provider yielding `nil` makes both conditional forms fail conservatively, without silent built-in fallback. DLSI's spell-name path resolves rank-stripped spell IDs and preserves canonical school/CC/dispel composition; do not conflate lack of an immune fact with proven vulnerability.
- **Data safety:** original file name `SuperCleveRoidMacros_Immunity.db`, schema version 1, and existing facts/hypotheses persist untouched. Storage opens before Knowledge and UI activation; mismatched version, nonempty unversioned schema, failed validation and missing HearthDB fail closed. No startup `ResetSchema`, delete, silent migration or merge. Handle closes on logout. Legacy `CleveRoids_ImmunityData` and `CleveRoidMacros.immunityBackups` stay host-owned and preserved, with DLSI UI backup/clear/restore/delete mutators disabled; DLSI never reads or displays host legacy records. DLSI target diagnostics read their *own* Knowledge facts, not host legacy conclusions.
- All named UI/event/model frames use DLSI names; original layout is retained. Private `/dlsi` command opens original DLSI UI without overwriting host commands.
