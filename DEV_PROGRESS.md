## Implemented architecture and invariants

1. **Observation ownership:** one private `SCRM_DLSI_ObservationFrame` normalizes Nampower events, with two private listeners (transient context and Knowledge). Observation handling is gated by both DLSI readiness and live provider selection. No parallel SCRM observer or host-data mutation was introduced.
2. **Host provider contract:** host `ImmunityProviders.lua` on `immunities-hook` exposes `RegisterImmunityProvider(id,name,check)` and `GetSelectedImmunityProvider()`. DLSI registers `scrm-dlsi` only after successful storage initialization, v1→v2 repair if required, v2→v3 migration if required and module activation. The query returns **true = positively immune, false = positively vulnerable for a complete query, nil = unknown**; selected-but-unavailable host providers must not fall back to SCRM legacy state. The host macro `[immune]` and `[noimmune]` treat an external unknown as neither proved immune nor proved nonimmune. DLSI debug/UI and Knowledge query only its own HearthDB conclusions.
3. **DB:** `SuperCleveRoidMacros_Immunity.db`, schema v3. Fresh empty DB initializes directly at v3; existing v1 runs the original repair to v2 first; v2 migrates to v3; v3 reruns do nothing. Unsupported/unversioned/corrupt or failed upgrades close without registering the provider. v3 archives `dlsi_v3_fact_backup`, `dlsi_v3_hypothesis_backup`, `dlsi_v3_hypothesis_candidate_backup` retain retired ambiguous immune facts and untyped historical hypotheses/candidates with reasons; `dlsi_aura_repair_backup` remains untouched. No mob/spell allowlist and no startup resets. See `docs/hearthdb-v3-recovery.md` for cold backup and restore.
4. **Inference:** DBC profile tracks each of three effect slots, explicit mechanic vs valid zero-mechanic aura fallback, raw IDs, unknown target applicability. Candidate builder retains typed multi-source provenance and uncertainties and never treats DBC possibility as attributable IMMUNE proof. `IMMUNE` and `IMMUNE2` stay distinct. Shared proof gate protects both immediate and delayed hypothesis singleton promotions. Generic immune events and candidate elimination alone cannot write permanent immune facts; true correlated damage/effect success can establish vulnerability and revoke past immune conclusions. Player identity, absent target identity, temporary guards, DR, reflections and dynamic observations remain guarded. New persisted hypotheses require complete typed candidate context; real ClassicAPI lacks implicit effect target fields, so this path is typically withheld.
5. **Chat 5 correction:** `BuildQueryDimensions` now requires `profile.effectClassificationComplete == true` and `profile.targetApplicabilityComplete == true` before returning **false** for a spell query. This fixes a demonstrable gap where unclassified/unknown-target effects could be overlooked by the provider, incorrectly claiming the whole spell vulnerable. Independently confirmed positive immunity and named school queries remain available. Given real implicit target data is unavailable, spell-query vulnerability often remains **nil** rather than an unsupported false; this is intentional safety debt until proper metadata/runtime proof exists.
